# 배송관리 시스템 설계 문서

> 대상 시스템: **settlementmanager** (확장)
> 작성일: 2026-07-25
> 개발 환경: Claude IDE(Claude Code) 기반 개발 예정
> 범위: ① 배송 도메인·상태모델 신설(우선) → ② 신청↔매출 연계 → ③ 배송목록 전송

---

## 0. 결론 요약

배송관리는 **별도 시스템이 아니라 settlementmanager 내부 확장**으로 구축한다.
이유는 배송의 출발점인 **교재구매 신청(모바일 신청·OCR·관리자 대장·PDF·Drive 저장)이 이미 settlementmanager에 완성**되어 있고, 필요한 인프라(메일·xlsx·PDF·Drive·인증·크론)가 전부 재사용 가능하기 때문이다.

실제 신규 작업은 "새 시스템 구축"이 아니라 아래 4가지다.

1. `shipments` / `shipment_log` 테이블 신설 + 배송 상태모델 (← **1번, 우선**)
2. `sales`에 `textbook_application_id` · `source='textbook'` 추가 → 신청↔매출 연계 (← **2번**)
3. 배송관리 화면(`features/delivery`) + 배송 API
4. 배송목록 전송(기존 메일/xlsx 인프라 재사용)

**착수 순서 (2026-07-26 확정)**

```
Phase 1   배송 도메인·상태모델
Phase 1.5 서버 인증·인가          ← 선결 과제(현재 /api/* 전부 무인증)
Phase 2   신청↔매출 연계
Phase 3   배송목록 전송
Phase 4   배송추적 자동화
Phase 5   신청 진입 분리 · 점주 온보딩   ← 인가 완료 후에만
```

## 2. 배송 상태모델 (1번 핵심)

### 2.1 상태 정의

**대전제: 접수 ≠ 배송.** 신청 접수 시점에 배송지가 확정되지 않을 수 있고(현장 실무상 **"추후배송"** 조건이 존재), 이 건들은 배송 대상으로 확정하기 전 단계에 머문다.

```
접수 ─┬─────────────→ 목록확정 → 전송완료 → 배송중 → 배송완료 → 완료확인
      └→ 추후배송 ──↗
         (배송지 미확정)
                    └ (전송 전 언제든) → 취소
```

| status | 의미 | 진입 트리거 |
| --- | --- | --- |
| `접수` | 교재신청 접수 시 자동 생성 | 신청 등록(`createApplication`) |
| `추후배송` | **배송지 미확정 — 배송 시점·주소가 정해지지 않은 보류 상태** | 접수 시 배송지 미비, 또는 관리자 보류 지정 |
| `목록확정` | 배송 대상으로 확정(배송지 스냅샷 고정) | 관리자 확정 — **배송지 필수 검증 통과 시에만** |
| `전송완료` | 물류업체로 배송목록 메일 전송됨 | 목록 전송 API |
| `배송중` | 송장번호 등록 | 관리자 송장 입력(또는 택배사 API) |
| `배송완료` | 택배사 배송완료 | 수동 변경(추후 조회 자동화) |
| `완료확인` | 최종 확인 | 관리자/고객 확인 |
| `취소` | 배송 취소 | 전송 전 단계에서만 |

> `추후배송` 건은 배송목록 전송 대상에서 **자동 제외**된다. 배송지가 확정되면 `목록확정`으로 전이시켜 정상 흐름에 합류시킨다.

### 2.2 신청↔배송 관계

- 기본 **1 신청 : 1 배송건**. (분할배송이 필요해지면 `shipments` 다건 허용으로 확장 — 스키마는 이미 대응 가능)
- **신청 접수 시 `shipments` 1행 자동 생성**(배송지/교재 스냅샷 복사). → 배송관리 대장에서 신규 신청이 누락 없이 바로 보인다.
- 초기 상태는 **배송지 유무로 분기**한다: 배송지가 있으면 `접수`, 없으면 `추후배송`.
- 배송지 등은 신청 원본에서 복사하되, 배송건에서 별도 수정 가능(스냅샷). 신청 원본 수정과 분리한다.

**실패 처리 원칙 — 신청 성공을 우선한다**

배송행 자동 생성이 실패해도 **신청은 성공 처리**한다. 배송 생성 실패는 **로그만 남기고**, 누락 건은 배송관리 대장에서 **사후 보정**한다.
→ 배송 생성 오류 때문에 신청 접수가 막히면 안 된다(현장 신청이 최우선 경로).

### 2.3 상태 전이 규칙표

`setStatus(id, toStatus, actor, memo)`는 아래 표에 없는 전이를 **거부**한다. 임의 점프(예: `접수 → 배송완료`)를 막기 위함이다.

| from \ to | 추후배송 | 목록확정 | 전송완료 | 배송중 | 배송완료 | 완료확인 | 취소 |
| --- | :-: | :-: | :-: | :-: | :-: | :-: | :-: |
| **접수** | ● | ●¹ | | | | | ● |
| **추후배송** | | ●¹ | | | | | ● |
| **목록확정** | ● | | ● | | | | ● |
| **전송완료** | | | | ● | | | |
| **배송중** | | | | | ● | | |
| **배송완료** | | | | ●² | | ● | |
| **완료확인** | | | | | | | |
| **취소** | | | | | | | |

¹ `목록확정` 진입 시 **배송지(주소·수령인·연락처) 필수 검증**. 미충족이면 거부하고 `추후배송` 유지.
² 오배송·반송 등 예외 복구 경로. 관리자 권한 + `memo` 필수.

- `완료확인`·`취소`는 **종료 상태**로, 이후 전이 없음.
- `전송완료` 이후에는 취소 불가 — 이미 물류업체로 나간 건이므로 별도 협의 대상.
- 모든 전이는 `shipment_log`에 `from_status`·`to_status`·`actor`·`memo`와 함께 기록한다.

## 3. DB 스키마 (신규/변경)

`server/schema.sql` 하단에 아래를 추가하고, `scripts/initDb.js`(멱등 실행)로 반영한다.

### 3.1 신규: `shipments`

```sql
-- ══════════════════════════════════════════════════════════════
-- 배송관리 (교재구매 신청 → 배송 라이프사이클)
--   · 신청 1건당 배송 1건 자동 생성. 배송지/교재는 신청 시점 스냅샷.
-- ══════════════════════════════════════════════════════════════
CREATE TABLE IF NOT EXISTS shipments (
  id                      TEXT PRIMARY KEY,                 -- S0001 (MAX+1)
  textbook_application_id TEXT REFERENCES textbook_applications(id) ON DELETE SET NULL,
  -- 배송지 스냅샷 (신청 시점 복사, 배송건에서 수정 가능)
  recipient_name          TEXT,
  phone                   TEXT,
  address                 TEXT,
  delivery_memo           TEXT,
  book1_name              TEXT,
  book2_name              TEXT,
  -- 상태 / 추적
  status                  TEXT NOT NULL DEFAULT '접수',      -- 접수/목록확정/전송완료/배송중/배송완료/완료확인/취소
  carrier                 TEXT,                             -- 택배사
  tracking_no             TEXT,                             -- 송장번호
  batch_id                TEXT,                             -- 목록 전송 배치 식별(한 번에 보낸 묶음)
  sent_to_logistics_at    TIMESTAMPTZ,                      -- 물류업체 전송 시각
  shipped_at              TIMESTAMPTZ,                      -- 발송(송장등록) 시각
  delivered_at            TIMESTAMPTZ,                      -- 배송완료 시각
  confirmed_at            TIMESTAMPTZ,                      -- 완료확인 시각
  memo                    TEXT,
  created_at              TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at              TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_shipments_status ON shipments(status);
CREATE INDEX IF NOT EXISTS idx_shipments_app    ON shipments(textbook_application_id);
CREATE INDEX IF NOT EXISTS idx_shipments_batch  ON shipments(batch_id);
```

### 3.2 신규: `shipment_log` (상태 전이 이력)

```sql
CREATE TABLE IF NOT EXISTS shipment_log (
  id           BIGSERIAL PRIMARY KEY,
  shipment_id  TEXT NOT NULL REFERENCES shipments(id) ON DELETE CASCADE,
  from_status  TEXT,
  to_status    TEXT,
  actor        TEXT,                                       -- 처리자(이메일/이름)
  memo         TEXT,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_shipment_log_shipment ON shipment_log(shipment_id);
```

### 3.3 변경: `sales` (2번 — 신청↔매출 연계)

```sql
-- 매출 원천에 textbook 추가: source = 'sale' / 'contract' / 'textbook'
ALTER TABLE sales ADD COLUMN IF NOT EXISTS textbook_application_id TEXT
  REFERENCES textbook_applications(id) ON DELETE SET NULL;
CREATE INDEX IF NOT EXISTS idx_sales_textbook_app ON sales(textbook_application_id);
```

> 기존 정책("교재신청 결제/입금은 매출관리에서 별도 처리")을 유지하면서, FK만으로 신청↔매출을 느슨하게 연결한다. 결제정보 로그는 기존 `sales` + `sales_installments` 구조를 그대로 사용한다(신규 테이블 불필요).

## 4. 백엔드 구현

### 4.1 신규 파일: `server/shipmentRepo.js`

`textbookRepo.js` 패턴을 그대로 복제한다.

- `mapShipment(row)` — snake→camel, `isoDate()`로 시각 변환
- `listShipments(filter)` — `{ startDate, endDate, status, buyer, batchId }`
- `getShipment(id)`
- `createShipment({ textbookApplicationId, ... })` — `S%04d` MAX+1 채번
- `createFromApplication(app)` — **신청 접수 시 호출**(배송지/교재 스냅샷 복사). 초기 status는 **배송지 유무로 분기**: 있으면 `접수`, 없으면 `추후배송`
- `updateShipment(id, patch)` — carrier/tracking_no/address/memo 등
- `setStatus(id, toStatus, actor, memo)` — **§2.3 전이 규칙표 검증** → status 갱신 + `shipment_log` 기록 + 해당 `*_at` 타임스탬프 세팅. 규칙표에 없는 전이는 거부
- `markSent(ids, batchId)` — 목록 전송 시 일괄 `전송완료` + `batch_id`·`sent_to_logistics_at`. **`추후배송` 건은 대상에서 제외**

### 4.2 `server/textbookRepo.js` 수정 (자동 배송 생성)

`createApplication()` 성공 **직후 별도로** `shipmentRepo.createFromApplication(app)`를 호출한다.

**트랜잭션 경계 — 신청과 배송을 묶지 않는다.**

```js
const app = await createApplication(data)          // ① 신청 저장 (커밋)
try {
  await shipmentRepo.createFromApplication(app)    // ② 배송행 생성
} catch (e) {
  console.error('[shipment] 자동 생성 실패', app.id, e.message)   // 로그만
}
return app                                          // ①은 반드시 성공 반환
```

- ②가 실패해도 **①을 롤백하지 않는다.** 신청 접수는 현장 최우선 경로이므로 배송 생성 오류로 막히면 안 된다.
- 누락 건은 배송관리 대장에서 **사후 보정**한다(신청 있는데 배송행 없는 건 조회 → 수동 생성).

### 4.3 신규 API (`server/index.js`, 기존 REST 스타일 준수)

```
GET    /api/shipments                      # 목록(기간/상태/구매자/배치 필터)
GET    /api/shipments/:id                  # 상세(+ shipment_log)
PATCH  /api/shipments/:id                  # 배송지/택배사/송장/메모 수정
POST   /api/shipments/:id/status           # 상태 전이 { toStatus, memo } + 이력
POST   /api/shipments/send-list            # { ids[] | filter } → xlsx 생성 → 물류 메일 전송 → 전송완료 일괄
GET    /api/system/config/delivery-email   # 물류 수신 이메일 조회 (app_settings)
PATCH  /api/system/config/delivery-email   # 물류 수신 이메일 저장
```

### 4.4 배송목록 전송 구현 (3번)

`/api/report/send` + `cron/daily-sales-report` 로직을 템플릿으로:

1. 대상 배송건(목록확정 상태) 조회 → `exceljs`로 배송목록 xlsx 생성 (접수번호·수령인·연락처·배송지·배송메모·교재1/2)
2. `app_settings.delivery_recipient_emails` 수신자에게 `getMailer().sendMail()` 발송
3. 성공 시 `markSent(ids, batchId)` → 상태 `전송완료`
4. (선택) `/api/cron/daily-delivery-list`로 정기 자동 전송 — 기존 크론 + `CRON_SECRET` 보호 패턴 재사용

### 4.5 결제(분할결재) 처리 — 기존 `sales` 로직 **그대로 재사용**

교재구매 결제는 **별도 결제 테이블을 만들지 않는다.** 기존 매출(`sales` + `sales_installments`)에 등록하고, `salesRepo.createSale/updateSale`의 분할결재 로직을 손대지 않고 그대로 쓴다. (기존 정책: "교재신청 결제/입금은 매출관리에서 별도 처리")

**재사용되는 구조**

```js
payment = {
  method,            // 카드/현금/혼합/없음 — deriveMethod()가 자동 판정
  totalAmount,
  cardInstallments: [{ seq, amount, issuer, cardNumber, approvalNo,
                       terminalNo, serialNo, transactionDate, driveFileId, driveViewUrl }],
  cashInstallments: [{ seq, amount, approvalNo, transactionDate, identifierType, identifierNo,
                       merchantName, merchantBizNo, bank, depositor, driveFileId, driveViewUrl }],
}
```

- 저장은 트랜잭션(BEGIN/COMMIT/ROLLBACK)으로 묶여 회차 정합성이 보장된다.
- `method='없음'`이 지원되므로 **신청 접수 → (나중에) 결제 등록** 흐름이 자연스럽다. **배송 진행과 결제 확정을 분리 관리**한다.
- 실제 흐름: 신청 접수(결제 입력 없음) → 매출등록에서 결제 입력 → `textbook_application_id`로 신청과 연결(§5.3)

**적용 시 보완할 4가지 (기존 코드의 한계)**

1. **금액 검증 부재** — `totalAmount`와 회차 합계 일치 여부를 서버가 검증하지 않는다. 교재는 현장(파트너·점주)에서 입력되므로 불일치 위험이 크다. → **서버 검증 추가**
2. **회차 수 제한 부재** — "최대 6회"는 스키마 주석에만 있고 서버는 무제한 삽입 가능. → 입력 폼에서 제한
3. **`updateSale`의 전체 삭제·재삽입** — `DELETE FROM sales_installments` 후 재INSERT라, 회차에 붙은 **전표 이미지 링크(`drive_file_id`)가 유실**된다. → 수정 화면에서 기존 링크를 반드시 함께 전송
4. **입력 필드가 계약·매출 기준으로 과다** — 단말기번호·일련번호·가맹점 사업자번호 등. → 저장 구조는 유지하되 **신청/교재용 화면은 금액·승인번호·거래일 중심의 축소 폼** 사용

### 4.6 배송추적 전략 — 접수는 수동, 추적만 API

**대전제: "접수(송장발급) API"와 "조회(추적) API"는 완전히 다른 서비스다.** 이 둘을 분리해서 판단해야 한다.

| 구간 | 성격 | 권장 방식 |
| --- | --- | --- |
| ① 접수·송장발급 | **택배사 실계약 전제**. 계정 기반 등록 API 필요 | **수동** (물류담당자가 택배사에서 접수) |
| ② 송장번호 입력 | 접수 결과 회신 | **수동** — 화면 입력 또는 회신 엑셀 업로드 |
| ③ 배송추적 | 송장번호만 있으면 자동화 가능 | **API 자동화** ← 여기서 효과가 가장 크다 |

**결론: "일부 수동입력 + 추적만 API"가 정확히 맞는 전략이다.** ①②는 택배사 계약·물류업체 확정에 묶여 있어 지금 자동화해도 효용이 적고, ③은 송장번호 하나만 있으면 즉시 자동화되며 담당자의 반복 조회 업무를 없앤다.

**추적 API 후보 (2026-07 기준 조사)**

- **스마트택배(스윗트래커)** — 배송조회/추적 API, API Key 방식. 국내에서 가장 널리 쓰이는 조회 API. **접수·송장발행은 제공하지 않음**(조회 전용) — "스마트배송 API"로 접수까지 될 것으로 기대하면 안 된다.
- **Delivery Tracker** — 조회 API + **웹훅(Tracking Webhook) 지원**, 클라우드/셀프호스팅 선택 가능.
- **택배API(deliveryapi.co.kr)** — 조회가 아닌 **접수·송장발급**까지 지원(택배사 계정 기반). 단 지원 택배사가 **롯데택배·CJ대한통운**으로 한정, 월 100회 무료. → ③이 아니라 ①을 자동화할 때(3단계) 후보.

**아키텍처 원칙 — 추적 수단을 갈아끼울 수 있게 추상화**

`shipments`에 이미 `carrier`·`tracking_no`가 있으므로, 추적 수단은 서비스 계층으로 분리해 **수동/스마트택배/Delivery Tracker를 교체 가능**하게 만든다.

- 신규 `server/services/trackingService.js` — `track(carrier, trackingNo)` 단일 인터페이스. 내부 구현만 교체.
- **API가 실패해도 수동 상태변경 경로는 항상 남긴다**(폴백 필수). 외부 API 장애가 배송 업무를 막으면 안 된다.

```sql
ALTER TABLE shipments ADD COLUMN IF NOT EXISTS tracking_provider TEXT;   -- manual/sweettracker/...
ALTER TABLE shipments ADD COLUMN IF NOT EXISTS tracking_status_text TEXT;-- 택배사 원문 상태
ALTER TABLE shipments ADD COLUMN IF NOT EXISTS last_tracked_at TIMESTAMPTZ;
ALTER TABLE shipments ADD COLUMN IF NOT EXISTS tracking_raw JSONB;       -- 원본 응답 보관
```

**갱신 방식: 웹훅보다 크론 폴링 권장**

settlementmanager엔 이미 Cloud Scheduler 크론(`/api/cron/daily-sales-report`, `CRON_SECRET` 보호)이 돌고 있다. **`배송중` 상태 건만 하루 1~2회 조회**하는 `/api/cron/track-shipments`를 같은 패턴으로 추가하면 추가 인프라 비용이 0이다. 웹훅은 공개 엔드포인트·서명검증이 추가로 필요하므로 1인 개발 환경에선 폴링이 유리하다. 조회 결과가 완료면 `배송완료`로 자동 전이하고 `shipment_log`에 기록한다.

**단계**

1. **지금** — 수동 송장 입력 + 택배사 조회 **링크만** 제공(API 0건, 즉시 가능)
2. **다음** — 조회 API 연동 + 크론 폴링으로 `배송중 → 배송완료` 자동 전이
3. **선택** — 접수 API. **물류업체·택배사가 확정된 뒤에만** 검토(롯데/CJ면 가능). 무료 한도(월 100회)와 실제 물량을 먼저 대조할 것

**핵심 원칙 — las-mgmt는 "읽기 전용 신원 소스", 인증·신청은 settlementmanager로 일원화**

las-mgmt는 개발 후 시간이 많이 경과했으므로 **코드를 일절 수정하지 않는다.** 점주/점장 데이터만 읽어서 활용한다.

| 구분 | las-mgmt (Supabase) | settlementmanager |
| --- | --- | --- |
| 스택 | Supabase(Postgres) + `users` 테이블 | Firebase Auth + Cloud SQL(`staff_accounts`) |
| 점주/점장 | **원천(source of truth)** — `user_type`='점주'/'점장', LAS코드(LAS1000~2999), 지점, 연락처 | 본인확인 통과 시 계정 자동 생성 |
| 이 프로젝트에서의 역할 | **읽기 전용 조회만** (무수정) | 인증·신청·배송·매출 전부 처리 |

**las-mgmt 인증 실태 (코드 조사 결과 — 이 방침의 근거)**

| 발견 | 근거 |
| --- | --- |
| `users` 테이블에 **평문 비밀번호 저장** | `Login.jsx:24-34` — 비번이 `las0000`/`123456`이면 `users`에서 `.eq('password', password)`로 직접 대조해 로그인 |
| 공유 임시비번이 실제 유통 중 | 위 두 값이 코드에 하드코딩된 폴백 |
| 마이그레이션 미완료 | `MyInfo.jsx:132` — 비번 변경자만 `password='MIGRATED_TO_SUPABASE_AUTH'`. **미변경자는 아직 평문** |
| 정상 경로는 Supabase Auth | `auth.signIn()` → `users.auth_uid` 조인 |

> **컬럼명 정정**: LAS 고유번호의 실제 컬럼은 `las_code`가 아니라 **`users.referral_code`**다. 점주/점장 = `LAS1000~2999`, `user_type`으로 구분, `status='approved'` 승인 플래그.

**인증 방침 (확정)**

> **비밀번호는 어떤 형태로도 가져오지 않는다. 이메일은 식별자로만 재사용한다. 본인확인은 "그 이메일로 보낸 링크 클릭"으로 한다.**

- **비번 미사용 이유**: 평문 저장 + 공유 임시비번 상태에서 그 자격증명을 신뢰하면 las-mgmt의 취약점을 그대로 상속한다. Supabase Auth 위임도 불가 — 누가 마이그레이션 완료됐는지 구분할 수 없고 타 시스템 인증에 종속된다.
- **LAS코드+이름 대조만으로는 부족**: LAS코드는 `1000~2999` 순차 채번이라 추측 가능하고 이름은 비밀이 아니다. 이 조합은 *"명단에 있는가"*만 확인할 뿐 *"본인인가"*는 확인하지 못한다 → 사칭 가능. **이메일 소유 확인 단계를 반드시 붙인다.**
- **임시 비밀번호를 발송하지 않는다.** 비밀번호 **설정 링크**를 보내 본인이 직접 설정하게 한다(아무도 비번을 모름). 기존 [staffRepo.js `approveRequest`](../server/staffRepo.js)와 동일 패턴: `auth.createUser` → `generatePasswordResetLink` → `getMailer().sendMail`.

**점주 온보딩 흐름 (재가입·재입력 없음)**

```
① 점주 최초 접속 (신청 전용 URL)
② LAS 고유번호 + 이름 입력                    ← 본인확인 1단계: 명단에 있는가
③ 서버(service_role)가 las-mgmt users 조회·대조 — 브라우저에서는 절대 조회 금지
     referral_code = ? AND name = ?
     AND user_type IN ('점주','점장') AND status = 'approved'
④ 일치 → las-mgmt 등록 이메일로 "비밀번호 설정 링크" 발송
                                                ← 본인확인 2단계: 그 메일의 주인인가
     · 화면에는 마스킹만 표시 (ab***@gmail.com)
     · 불일치해도 동일 문구 응답 → LAS코드 존재 여부조차 노출 금지
⑤ 본인이 링크에서 비밀번호 직접 설정 → Firebase 계정 생성
⑥ staff_accounts 생성/갱신 (roles에 'store_owner' 추가, las_code=referral_code, branch, name, phone)
⑦ 이후 settlementmanager 자체 로그인 — las-mgmt 재조회 없음
```

- las-mgmt 조회는 **최초 온보딩 1회뿐**이다. 계정 생성 후에는 다시 조회하지 않는다.
- 점주 명단이 자연스럽게 settlementmanager로 이관되어, 추후 las-mgmt를 폐기해도 영향이 없다.
- **las-mgmt 코드는 일절 수정하지 않는다**(읽기 전용 service_role).

**계정 생성 위치 — `staff_accounts` (사용자관리 탭 아님)**

시스템관리의 두 탭은 실체가 다르다. 점주 계정은 **파트너 계정관리 쪽**에 만들어진다.

| 탭 | 실체 | 저장소 | 실제 로그인 |
| --- | --- | --- | --- |
| 사용자관리 | `userStore.ts` **localStorage 목업** | 브라우저 로컬 | ❌ 불가 (비번 초기화도 `alert()`만 띄우는 자리표시자) |
| 파트너 계정관리 | `staff_accounts` + Firebase Auth | Cloud SQL | ✅ 실계정 ← **점주는 여기** |

**역할 구조 — 점주/점장이 기반, 파트너/파트장은 그 위에 얹는 자격 (2026-07-26 확정)**

파트너/파트장과 점주/점장은 대등한 두 축이 아니다. **점주/점장이 계정의 기반**이고,
그중 **LAS-On 사업 참여를 원하는 사람이 파트너/파트장 자격을 "요청"**하는 구조다.

| 구분 | 역할 | 부가정보 | 성격 |
| --- | --- | --- | --- |
| 기반 | `store_owner`(점주) / `store_manager`(점장) | `business_unit`, `branch`, `las_code` | 가입 시 **필수**, 둘 중 배타 |
| 추가 자격 | `part_leader`(파트장) / `field_partner`(파트너) | `part` | **요청 → 승인**, 둘 중 배타 |
| 관리 | `admin` | — | — |

```
roles = ['store_owner']                    ← 일반 점주
roles = ['store_owner', 'part_leader']     ← LAS-On 참여 점주(파트장)
roles = ['part_leader']                    ← 신규로는 생기지 않음(기존 계정만, §과도기)
```

→ `role` 단일 컬럼을 **`roles TEXT[]` 다중 역할**로 바꾸고, **권한은 보유 역할 권한의 합집합**으로 계산한다. 부가정보는 컬럼이 달라 충돌 없이 공존한다.

**LAS-On 자격 요청 시점은 2가지**

1. **가입과 동시** — 점주/점장 가입 폼에서 "LAS-On 사업 참여" 선택 + 희망 자격(파트너/파트장)
2. **가입 후 별도** — 로그인한 점주/점장이 참여 신청 → 관리자 승인 → `roles`에 추가

**"선택"이 아니라 "요청"이다 — 승인은 분리 판단한다**

신청자가 체크했다고 자동 부여되면 안 된다. 승인 화면에서 **계정 승인과 LAS-On 자격 승인을
따로** 처리할 수 있어야 한다("점주는 승인, LAS-On은 보류"가 실제로 자주 발생).

**신규 가입 정책 (확정)**

- **파트너/파트장 단독 가입은 중단**한다. 신규는 반드시 점주/점장으로 가입한 뒤 LAS-On 자격을 요청한다.
- 공개 가입 페이지(`/staff-request`)는 점주/점장 기반 폼으로 개편한다(URL 유지).

**과도기 — 기존 계정 정보 보정**

기존 목록은 점주/점장 여부를 확인하지 않고 파트너로 등록해 왔다. **점주가 아닌데 파트너로
등록된 건이 섞여 있을 수 있어 오프라인 확인이 필요**하다. 과도기 동안 아래 순서로 보정한다.

1. 관리자 계정관리 목록에서 **`roles`에 `store_owner`/`store_manager`가 없는 파트너 계정**을 추린다(= 미보정 대상). 별도 플래그 없이 roles 만으로 판별 가능하다.
2. 오프라인으로 점주/점장 여부를 확인한다.
3. 확인되면 계정관리 상세에서 기반 역할(+사업부·지점)을 추가한다.
4. 점주가 아닌 것으로 확인되면 별도 처리(유지/비활성)를 개별 판단한다.

> 보정 전이라도 **인가는 정상 동작**한다 — 권한이 합집합이라 `roles=['field_partner']`만 있어도 매장섭외관리는 그대로 열린다. 보정은 데이터 정합성 작업이지 접근 차단 작업이 아니다.

**동일인 판정 (계정 쪼개짐 방지)**

- **이메일이 1차 키**. 온보딩 시 그 이메일이 이미 `staff_accounts`에 있으면 **새 계정을 만들지 않고 기존 계정 `roles`에 역할만 추가**한다.
- 이메일이 다르면 **전화번호로 후보를 찾아 관리자 확인 후 병합**한다. **자동 병합은 하지 않는다.**

**보안 (필수 준수)**

- `las-mgmt/src/lib/supabase.js`의 키는 **anon(공개) 키**다. `users` 조회는 **브라우저에서 절대 하지 않고**, settlementmanager **서버에서 service_role 키(비공개, `.env`)로만** 수행한다.
- 조회 컬럼은 최소화: `referral_code`, `name`, `email`, `phone`, `branch`, `user_type`, `status`만 SELECT. 민감정보(주민번호 등) 미조회.
- 대상 한정: `user_type IN ('점주','점장') AND status = 'approved'`.
- **rate limit**: IP당 시간당 5회 + LAS코드당 3회 (무차별 대입 차단).
- 비밀번호 설정 링크 **만료 1시간**(Firebase 기본).
- 이미 가입된 계정이면 "이미 가입된 계정입니다. 로그인해 주세요" 안내.

> **별도 보고 (las-mgmt 자체 리스크)**: `users`에 평문 비밀번호가 남아 있는 한 보안이 전적으로 Supabase RLS 설정에 의존한다. RLS 상태는 클라이언트 코드로 확인할 수 없으므로 las-mgmt 쪽에서 `users` 테이블 RLS 정책 점검이 필요하다. (본 프로젝트에서 코드는 수정하지 않는다.)

**DB 변경**

```sql

UPDATE staff_accounts SET roles = ARRAY[role] WHERE roles = '{}';   -- 기존 데이터 이관
-- 값: admin / part_leader / field_partner / store_owner / store_manager

ALTER TABLE staff_requests ADD COLUMN IF NOT EXISTS business_unit TEXT;
ALTER TABLE staff_requests ADD COLUMN IF NOT EXISTS branch        TEXT;
```

**신규 파일·API**

- 의존성: `server/package.json`에 `@supabase/supabase-js` 추가

## 7. 개발 시 주의(기존 코드 정합성)

- **ID 채번**: 중간 삭제 대비 `COUNT+1` 금지, `MAX(CAST(...))+1` 사용 (textbookRepo 참조).
- **날짜/시각**: 모든 출력은 `isoDate()` KST(+9h) 변환.
- **한글 PDF/폰트**: 컨테이너에 한글폰트 없음 → `server/fonts/NanumGothicBold.ttf` 번들 사용(pdfService 참조).
- **메일 미설정 폴백**: `getMailer()`가 null이면 500 응답 — `GMAIL_APP_PASSWORD` 또는 `SMTP_*` 필요.
- **크론 보호**: 모든 `/api/cron/*`는 `x-cron-secret` 헤더(`CRON_SECRET`) 검증.
- **파일 실물**: DB엔 `drive_file_id`/`drive_view_url` 링크만, 실물은 Drive(개발 시 로컬 폴백).

| **권한별 데이터 범위 제한** | `config.filterByBranch` + `user.branch`로 지점 자동 한정, 시스템관리자만 전체 | 점주는 자기 지점 배송만, 관리자는 전체 (§5.4 `branch` 컬럼과 연결) |
| **다필드 통합검색 + 기간 필터** | `searchFields`를 `ilike` OR로 조합, 주문일 시작~종료 | 수령인·연락처·주소 통합검색 + 접수일 기간 |
| **CSV 한글 깨짐 방지** | `﻿` BOM 선행 + 쉼표/따옴표/개행 이스케이프 | 원리는 채택하되 **출력은 xlsx로 격상**(아래 9.2) |

### 9.2 그대로 베끼면 안 되는 것 (개선 적용)

- **클라이언트에서 DB 직접 쿼리** — las-mgmt는 브라우저에서 Supabase를 직접 조회한다. settlementmanager는 **서버 API 경유**(`/api/shipments`)를 유지하고, 검색어는 서버에서 파라미터 바인딩한다.
- **CSV → xlsx** — settlementmanager엔 `exceljs`가 이미 있고 **물류업체 메일 첨부**에도 xlsx가 유리하다. 브라우저 CSV 생성 대신 서버 xlsx 생성으로 통일(§4.4와 동일 경로 재사용).
- **물리 삭제 금지** — las-mgmt는 관리자에게 `DELETE`를 준다. 배송은 **`취소` 상태 + `shipment_log` 이력**으로 관리하고 행을 지우지 않는다.
- **`alert()` 남용** — 조회·검색·오류를 전부 `alert`로 처리한다. settlementmanager 기존 패턴(화면 내 `loadErr` 표시)을 따른다.
- **페이지네이션 없음** — 전체 목록을 한 번에 로드한다. 배송건은 계속 누적되므로 **기간 기본값(예: 최근 1개월) + 페이지네이션**을 처음부터 넣는다.
- **인쇄 HTML 문자열 조립** — 사용자 입력이 그대로 HTML에 들어간다. 이식 시 **이스케이프 처리**를 추가한다.

### 9.3 인쇄 방식 선택

송장 출력은 두 경로가 있다. **1단계는 las-mgmt 방식(브라우저 `window.print`)을 권장**한다 — 이미 검증됐고 서버 부하·폰트 이슈가 없다. 신청서 PDF처럼 **파일로 보관·전달**해야 할 필요가 생기면 그때 서버 `pdf-lib`(한글폰트 번들 완비, `pdfService.js`) 경로로 옮긴다.
