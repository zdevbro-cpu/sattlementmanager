# 매장 임대차 관리 모듈 개발계획 (v2)

> Settlement Manager 신규 모듈 (Store Lease Management)
> v1 초안을 **실제 코드베이스 확인 결과**에 맞춰 개정한 판입니다.
> 개정 범위는 부록 A 참고 — 업무 요구(1~6장 내용)는 그대로 두고, 기술 전제·일정·구현 방식만 고쳤습니다.

---

## 1. 배경 및 목적

### 1.1 배경

- 전시 판매 매장을 급속히 확대 중
  - **라스브러리 (LASBRARY)** — 대형매장, 상가 단독 또는 대형 상업시설 입점
  - **라스온 (LAS-On)** — 소형매장, 병원·카페·마트 등 숍인숍 형태 입점
- 매장 수 증가에 따라 **부동산 상가 임대차 계약** 건수가 급증
- 계약서, 임대인 정보, 보증금·월세·관리비 등이 개인 파일/엑셀로 분산 관리되어 있어
  - 만기·갱신 통보 기한 누락 위험
  - 월 고정비 총액 파악 불가
  - 회계부서의 자료 요청 시 수작업 취합
- 회계관리 부서에서 **다양한 형태의 보고서**를 상시 요구

### 1.2 목적

1. 매장별 임대차 계약을 **단일 원장**으로 관리 (계약서 원본 + 조건 데이터화)
2. 보증금·월세·관리비 등 **고정비 발생/납부를 예측 가능**하게 관리
3. 계약 만기·갱신·인상 시점을 **자동 알림**으로 통제
4. 회계부서의 다양한 보고서 요구를 **파라미터 기반 리포트**로 대응
5. 본 모듈만 사용하는 담당자를 위한 **모듈 단위 접근 제한** 제공

## 2. 개발 범위 (Scope)

### 2.1 포함 ✅

| 구분 | 내용 |
|---|---|
| 임대차 계약서 관리 | 계약 등록/변경/갱신/해지, 원본 파일 첨부, 변경 이력 |
| 임대인 정보 관리 | 개인/법인, 사업자정보, 입금계좌, 연락처, 대리인 |
| 계약 조건 관리 | 보증금, 월세, 관리비, 부가세, 납부일, 인상 조건, 특약 |
| 비용 스케줄 | 월별 발생 예정액 산출, 실제 납부 대사 |
| 만기/갱신 관리 | 만기 D-day, 갱신 통보 기한, 자동 알림(메일) |
| 회계 리포트 | 고정비 명세, 보증금 잔액, 만기 현황, 브랜드/지역별 집계 (Excel 산출) |
| 모듈 전용 접근 | 본 모듈만 접근 가능한 전용 역할 및 라우팅 제한 |

### 2.2 제외 ❌ (본 모듈 범위 밖)

- **매장 마스터 관리** — 기존 `store_master` 그대로 사용, 신규 개발 없음
- 매장 인테리어·집기·시설물 관리
- 매장 매출/정산 로직 — 기존 매출관리 / 정산센터 유지
- 임대인 대상 전자계약 발송 (1단계 제외, 향후 검토)
- **회계 모듈 연동 (전표·출금 자동 생성)** — 미사용 예상으로 범위 제외
- 리스회계(K-IFRS 1116) 사용권자산·리스부채 자동 분개 → **4.6 참고, 옵션 처리**

> ⚠️ 범위 밖 항목은 이번 모듈 개발 시 코드를 건드리지 않습니다. 기존 `store_master`는 **읽기 전용**으로만 참조하며, 계약·매출·지급 관련 테이블은 **일절 수정하지 않습니다.**
> 회계 자료는 시스템 연동이 아닌 **리포트 Excel 산출물**로 회계부서에 전달하는 방식입니다.

## 3. 메뉴 구조

사이드바 `운영` 그룹에 **매장임대관리**를 추가합니다.
(계약관리 하위로 넣지 않는 이유는 4.1 참고)

현재 사이드바 구조는 [`web/src/components/layout/AppLayout.tsx`](../web/src/components/layout/AppLayout.tsx)의 `NAV_GROUPS` 한 곳에서 정의됩니다. 배열에 항목 1개를 추가하고 `BREADCRUMB`에 대응 항목을 넣으면 됩니다.

```
매장임대관리  (/lease)
   ├─ 임대차계약 목록·등록      (기본 화면)
   ├─ 임대료 납부관리
   ├─ 만기/갱신 현황
   └─ 임대차 리포트
```

> v1의 8개 서브메뉴는 화면 수를 과하게 늘립니다. 기존 모듈(계약관리·배송관리)은 **목록 화면 + 상세 드로어 + 모달** 조합으로 등록·수정·이력을 한 화면에서 처리합니다. 같은 패턴을 따르면 서브메뉴 4개로 충분하고, 사용자도 익숙한 조작을 하게 됩니다.

기존 메뉴 영향:

| 메뉴 | 변경 |
|---|---|
| 시스템관리 > 공통코드 | 비용항목·계약유형 등을 공통코드로 추가 (기존 `system_codes` 활용) |
| 통계 | 임대차 리포트는 임대관리 하위에 두고, 요약 지표만 통계에 노출 (Phase 5) |

## 4. 데이터 설계

### 4.1 설계 원칙 — 기존 계약(contract)과 분리

기존 `contracts` / `contract_history`는 **직원·점주·파트너와의 매출·수당 계약**입니다.
임대차 계약은 상대방(임대인), 금액 성격(비용), 라이프사이클(만기·갱신·묵시적 갱신)이 전혀 다릅니다.

→ **`store_lease`를 별도 테이블로 신설**합니다.

같은 테이블에 넣으면 정산·수당 계산이 오염됩니다. 실제로 2026-07 운영 데이터에서 **성격이 다른 데이터(임시저장 계약)가 같은 집계에 섞여 계약총액이 194억으로 부풀려진 사례**가 있었습니다. 임대차를 계약에 합치면 같은 문제가 구조적으로 반복됩니다.

### 4.2 신규 테이블 (9 → 6개로 축소)

```
lessor                 임대인 (개인/법인)
store_lease            임대차 계약 (본 모듈의 중심)
store_lease_history    계약 변경 이력 (스냅샷)
lease_charge_item      계약별 비용 항목 정의 (월세/관리비/기타)
lease_payment          실제 납부 내역 (예정은 저장하지 않음 — 4.5 참고)
lease_deposit          보증금 입출 내역 (납입/증감/반환)
lease_attachment       첨부파일 (계약서, 등기부, 사업자등록증, 도면, 사진)
```

v1 대비 변경:

- **`lease_schedule` 제거** — 월별 예정액은 저장하지 않고 계산으로 낸다 (4.5)
- **`lease_alert` 제거** — 알림 발송 이력은 `lease_payment`·`store_lease` 상태로 추적 가능하고,
  별도 테이블이 필요해지는 시점(재발송·수신확인 관리)까지 미룬다

### 4.3 주요 필드 정의

#### lessor (임대인)

| 필드 | 설명 |
|---|---|
| lessor_type | 개인 / 법인 |
| name | 성명 또는 법인명 |
| biz_reg_no | 사업자등록번호 (법인/일반과세자) |
| rep_name | 대표자명 |
| phone / email | 연락처 |
| bank_name / account_no / account_owner | 입금 계좌 |
| tax_invoice_type | 세금계산서 / 계산서 / 미발행 |
| agent_info | 대리인(부동산·관리단) 정보 |
| memo | 특이사항 |

#### store_lease (임대차 계약)

| 필드 | 설명 |
|---|---|
| id | 계약번호 (자동채번, 예: `LS-2026-0001`) |
| store_id | 매장 FK (`store_master`) — **NULL 허용** |
| brand | 라스브러리 / 라스온 |
| lease_type | 신규 / 갱신 / 재계약 / 승계 / 전대 / 해지 |
| lessor_id | 임대인 FK |
| road_address / detail_address | **소재지 (계약 시점 스냅샷)** |
| contract_area / exclusive_area | **면적 NUMERIC (계약 시점 스냅샷)** |
| floor_location | 층/호수 |
| contract_date | 계약체결일 |
| start_date / end_date | 임대차 기간 |
| deposit | 보증금 |
| monthly_rent | 월 차임 |
| maintenance_fee | 월 관리비 |
| vat_included | 부가세 별도/포함 여부 |
| payment_day | 납부일 (매월 N일) |
| payment_method | 계좌이체 / 자동이체 / CMS |
| rent_free_months | 렌트프리 개월수 |
| escalation_rule | 인상 조건 (연 N%, 매 N년 재협의 등) |
| renewal_notice_days | 갱신 통보 기한 (기본 만기 6개월~2개월 전) |
| restoration_clause | 원상복구 조건 |
| special_terms | 특약사항 (텍스트) |
| prev_lease_id | 갱신 전 계약 FK |
| status | 검토중 / 계약완료 / 진행중 / 만기예정 / 종료 / 해지 |
| created_by / updated_by / created_at / updated_at | 감사 필드 |

**소재지·면적을 다시 저장하는 이유** — `store_master`에 이미 `road_address`, `detail_address`, `total_area`, `available_area`, `floor_location`이 있습니다(10장 #6 확인 결과). 그런데도 중복 저장합니다.

1. **계약서에 적힌 면적이 법적 기준**입니다. 매장 마스터가 나중에 수정돼도 계약 조건은 바뀌면 안 됩니다.
2. `store_master.total_area`가 **`TEXT` 타입**이라 집계·정렬에 쓸 수 없습니다. 리포트에서 ㎡당 임차료를 내려면 `NUMERIC`이 필요합니다.
3. 계약 이전 단계(검토중)에서는 `store_master`에 아직 행이 없을 수 있습니다. 그래서 `store_id`를 NULL 허용으로 둡니다.

기존 계약관리도 같은 사고로 이력 스냅샷을 씁니다. 일관됩니다.

#### lease_charge_item (비용 항목)

계약마다 항목 구성이 다르므로 **가변 항목**으로 설계합니다.

| 필드 | 설명 |
|---|---|
| lease_id | 계약 FK |
| charge_type | 월세 / 관리비 / 공용전기 / 수도 / 광고분담금 / 주차비 / 기타 |
| amount | 금액 (정액) |
| calc_type | 정액 / 실비정산 / 매출연동(%) |
| vat_type | 별도 / 포함 / 면세 |
| cost_category | 비용 분류 코드 (리포트 집계·엑셀 산출용) |

> `charge_type`·`cost_category`는 시스템관리 **공통코드(`system_codes`)** 로 관리합니다. 기존에 택배사·구독상품을 같은 방식으로 다루고 있어 화면·API를 그대로 재사용할 수 있습니다.

#### lease_payment (납부 내역)

| 필드 | 설명 |
|---|---|
| lease_id | 계약 FK |
| year_month | 귀속 연월 (YYYY-MM) |
| charge_type | 항목 |
| planned_amount | 그 시점 예정액 (대사 근거로 함께 기록) |
| paid_date / paid_amount | 실제 납부 |
| diff_reason | 예정액과 차이 사유 (실비정산 등) |
| tax_invoice_no / tax_invoice_date | 세금계산서 |
| payer_account | 출금 계좌 (텍스트 기록) |
| status | 미납 / 납부완료 / 연체 / 보류 |

`(lease_id, year_month, charge_type)` 유니크 인덱스를 걸어 **중복 납부 기록을 DB에서 차단**합니다.

#### lease_deposit (보증금 원장)

보증금은 **비용이 아니라 자산**이므로 별도 원장으로 잔액을 관리합니다.

| 필드 | 설명 |
|---|---|
| lease_id | 계약 FK |
| tx_type | 납입 / 증액 / 감액 / 대체 / 반환 |
| tx_date | 발생일 |
| amount | 금액 |
| balance | 거래 후 잔액 |
| memo | 사유 |

### 4.4 상태 전이 규칙

```
검토중 ──▶ 계약완료 ──▶ 진행중 ──┬──▶ 만기예정 ──┬──▶ 종료
                                  │                └──▶ 갱신(신규 계약 생성, 이전 계약 종료)
                                  └──▶ 해지 (중도해지)
```

- `진행중` → `만기예정` : 만기 D-180 자동 전환 (크론)
- 갱신 시 **기존 계약을 수정하지 않고 새 계약 레코드 생성** + `prev_lease_id`로 연결
  → 이력 추적 및 과거 조건 조회 보장

**전이 규칙은 코드에 표로 선언**하고, 서버가 `FOR UPDATE` 잠금 아래에서 검증합니다.
배송관리 `shipmentRepo.js`의 `TRANSITIONS` 구조를 그대로 따릅니다 — 규칙에 없는 전이는 400으로 거부하고 사유를 화면에 그대로 보여줍니다.

### 4.5 월별 스케줄을 미리 만들지 않는다 ⚠️ (v1에서 변경)

v1은 계약 등록 시 `LeaseSchedule`을 기간 × 항목만큼 자동 생성하도록 했습니다. **이 방식은 물량에서 무너집니다.**

- 3년 계약 × 비용항목 4개 = **144행 / 계약**
- 매장 200개 → **약 28,800행**이 실적과 무관하게 미리 깔림
- 계약 조건이 바뀌면(인상·항목 추가) 이미 생성된 미래 행을 전부 다시 손봐야 함

교재 구독 정기발송에서 같은 판단을 이미 했습니다. 26회차를 미리 만들면 하루 20건 × 26 = 520행이 매일 쌓여 목록이 감당되지 않아, **예정일이 도래할 때 크론이 한 건씩 만드는 방식**으로 바꿨습니다.

→ **월별 예정액은 계약 조건에서 계산**하고, **실제로 납부·차이가 생긴 건만** `lease_payment`에 남깁니다.

| 필요한 것 | 방법 |
|---|---|
| 이번 달 나갈 총액 | 진행중 계약의 `lease_charge_item` 합계 (쿼리) |
| 향후 12개월 예상 | 계약 기간·인상조건으로 계산 |
| 납부 여부 | `lease_payment` 조회 — 행이 없으면 미납 |
| 연체 판정 | 크론이 `payment_day` 경과 + 행 없음 → 알림 |

렌트프리·중도 인상은 계산 함수 한 곳(`leaseCalc.js`)에 모아 리포트와 화면이 같은 결과를 쓰게 합니다.

### 4.6 리스회계 (옵션 · 1단계 제외)

- 일반기업회계기준 적용 시: **월 임차료를 단순 비용 처리** → 본 설계 기본값
- K-IFRS 1116 적용 필요 시: 사용권자산 / 리스부채 / 감가상각 / 이자비용 분개 필요
- 향후 요구 발생 시 별도 테이블을 추가하는 방식으로 확장
- **본 모듈은 자동 분개를 수행하지 않습니다.** 필요한 자료는 리포트(6장)로 산출하여 회계부서가 직접 처리

## 5. 화면 설계

### 5.1 화면 목록

기존 모듈과 같은 **목록 + 드로어 + 모달** 구성입니다.

| # | 화면 | 유형 | 비고 |
|---|---|---|---|

### 5.4 임대인 분리를 Phase 2로 미루는 이유

한 임대인이 여러 매장을 갖는 경우가 **실제로 얼마나 되는지 확인되지 않았습니다.** 드물다면 별도 화면·검색·중복정리 부담만 늘어납니다.

→ Phase 1에서는 `lessor` 테이블은 만들되 **계약 등록 화면에서 직접 입력**하게 하고, 목록 화면(L-05)은 Phase 2로 미룹니다. 데이터가 쌓이면 중복 임대인이 몇 명인지 바로 셀 수 있고, 그때 분리해도 늦지 않습니다.

## 6. 회계 리포트 설계

### 6.1 접근 방식 — 하드코딩 1종을 먼저, 엔진은 그다음 ⚠️ (v1에서 변경)

v1은 "요구가 자주 바뀌니 공통 리포트 엔진을 먼저 만들자"면서 정작 **Phase 4(8주차)** 에 배치했습니다. 그때쯤이면 회계부서는 이미 수기 요청을 하고 있습니다.

더 중요한 문제는, **실제로 어떤 컬럼이 필요한지 모르는 상태에서 엔진을 만들면 헛돕니다.** 파라미터·집계축을 무엇으로 열어둘지는 실제 양식을 봐야 정해집니다.

→ **Phase 1에 R-03(매장별 고정비 명세) 한 종을 하드코딩으로** 냅니다.
이 프로젝트에는 매출일일보고·배송목록·라스온현황 등 ExcelJS 산출 선례가 이미 있어 한 건 추가는 부담이 작습니다.
그 결과를 회계부서에 보여주고 피드백을 받은 뒤, **Phase 4에서 엔진으로 일반화**합니다.

```
[공통 리포트 엔진] — Phase 4
  ├─ 파라미터 영역 (기간 / 브랜드 / 지역 / 매장 / 임대인 / 상태)
  ├─ 집계 축 선택 (행: 매장·브랜드·지역·임대인 / 열: 월·분기·항목)
  ├─ 그리드 (소계·합계·비율 자동)
  └─ Excel 다운로드 (서식 포함)
```

> ExcelJS 작성 규칙은 [`CLAUDE.md`](../CLAUDE.md) 의 「엑셀 보고서 양식」 항목을 따릅니다.
> 특히 `cell.style = {...}` 일괄 대입, 병합셀 반복 스타일 금지는 실제로 사고가 났던 부분입니다.

## 7. 권한 설계

### 7.1 현재 권한 구조 (확인 결과)

10장 #7의 답입니다. **역할명 하드코딩이 아니라, 경로 단위 정책표 방식입니다.**

[`server/middleware/auth.js`](../server/middleware/auth.js)

- `staff_accounts.roles`가 **`TEXT[]` 다중 역할**이고 권한은 합집합으로 판정
- **경로 접두사 → 허용 역할** 표(`POLICY`)가 한 곳에 모여 있음
- **목록에 없는 경로는 admin 전용으로 기본 차단**(fail-closed)

```js
const POLICY = [
  { prefix: '/api/stores', roles: FIELD },
  ...
]
function policyFor(path) { ... return hit ? hit.roles : ['admin'] }  // fail-closed
```

→ **리팩터링이 필요 없습니다.** v1이 우려한 "역할명 하드코딩" 상황이 아닙니다.

### 7.2 신규 역할 — 권한 코드가 아니라 역할 2개로 ⚠️ (v1에서 변경)

v1은 `LEASE_VIEW` / `LEASE_EDIT` / `LEASE_PAYMENT` / `LEASE_REPORT` / `LESSOR_MANAGE` 5개 권한 코드를 제안했습니다. **현재 구조에 세분 권한 코드 개념이 없습니다.**

지금 도입하면 역할 기반과 권한코드 기반 **두 방식이 공존**하게 되고, 이후 모든 신규 기능이 어느 쪽을 따를지 매번 판단해야 합니다.

→ 담당자가 소수인 현 시점에는 **역할 2개로 충분**합니다.

| 역할 코드 | 명칭 | 접근 범위 |
|---|---|---|
| `lease_admin` | 임대관리 담당 | 임대차 전체 (등록·수정·납부·리포트) |
| `lease_viewer` | 임대관리 조회 | 조회·리포트만 |

세분 권한이 실제로 필요해지는 시점(예: 납부 처리는 재무만)에 권한 코드 체계를 **전사적으로** 도입하는 편이 낫습니다.

서버 변경은 정책표 한 줄입니다.

```js
const LEASE = ['admin', 'lease_admin', 'lease_viewer']
{ prefix: '/api/lease', roles: LEASE },
```

쓰기 API는 라우트 안에서 `req.user.roles`에 `lease_viewer`만 있으면 403으로 거부합니다.

### 7.3 모듈 전용 계정 — 이미 구조가 있습니다

v1이 설계한 4단 차단 중 **3단계까지 이미 구현되어 있습니다.**

| 단계 | v1 제안 | 실제 |
|---|---|---|
| 1. 인증 | Firebase Custom Claims | **Firebase ID 토큰 검증 + `staff_accounts` 역할 조회** — 동등한 효과, 역할 변경이 즉시 반영되는 장점 |
| 2. 메뉴 | 사이드바 렌더링 제외 | `AppLayout` `NAV_GROUPS`에 역할 조건 추가 |
| 3. 라우팅 | `RequirePermission` 가드 | **[`App.tsx`](../web/src/App.tsx)가 역할별로 라우트 자체를 다르게 렌더링** — 파트너는 `/mobile-stores`, 점주는 `/textbook-apply`로 이미 강제 |
| 4. API | 서버 미들웨어 | **`middleware/auth.js`가 이미 전 경로 검증** (fail-closed) |

→ **`App.tsx`의 기존 역할 분기에 `lease_admin` 갈래 한 줄만 추가**하면 전용 계정이 완성됩니다. 로그인 후 `/lease`로 진입하고 다른 경로는 접근 자체가 없습니다.

> Custom Claims를 쓰지 않는 이유 — claims는 토큰 갱신 전까지 반영되지 않아 역할을 회수해도 최대 1시간 남습니다. 현재 방식은 DB 조회라 즉시 반영됩니다. 굳이 바꿀 이유가 없습니다.

### 7.4 기존 역할 매핑

| 역할 | 계약 조회 | 계약 등록/수정 | 납부 처리 | 리포트 |
|---|---|---|---|---|
| admin | ✅ | ✅ | ✅ | ✅ |
| lease_admin | ✅ | ✅ | ✅ | ✅ |
| lease_viewer | ✅ | — | — | ✅ |
| 그 외 전원 | — | — | — | — |

**임대차는 기본적으로 비공개**입니다. 임대료·보증금은 민감 정보이고, 파트너·점주에게 노출할 이유가 없습니다. fail-closed 구조라 정책표에 넣지 않은 역할은 자동으로 차단됩니다.

## 8. 기술 구성 ⚠️ (v1 전면 수정)

v1의 기술 구성은 **실제 코드베이스와 달랐습니다.** 그대로 착수하면 Phase 1에서 방향이 어긋납니다.

| 영역 | v1 기재 | **실제** | 비고 |
|---|---|---|---|
| Backend | Cloud Functions | **Express on Cloud Run** | `server/index.js` 단일 앱 |
| DB 접근 | Prisma | **`pg` 직접 쿼리** | `server/schema.sql` + `*Repo.js` 패턴 |
| 스키마 관리 | Prisma Migrate | **`schema.sql` + `/api/admin/migrate`** | `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` |
| 상태/데이터 | TanStack Query | **`useState` + `*Store.ts`** | 패키지는 있으나 `main.tsx` 외 미사용 |
| 폼 | React Hook Form + Zod | **수동 `useState`** | Zod는 설치조차 안 됨 |
| 인증/권한 | Custom Claims | **ID 토큰 + `staff_accounts.roles`** | 7.3 참고 |
| 첨부 저장소 | Firebase Storage | **Google Drive** | `googleapis` + `drive.uploadFile` |
| 배치 | Cloud Scheduler | Cloud Scheduler ✅ | `/api/cron/*` + `CRON_SECRET` 헤더 |
| 리포트 | ExcelJS ✅ | ExcelJS ✅ | 서버·클라이언트 양쪽 사용 중 |
| Front | Vite + React + TS + Tailwind ✅ | 동일 ✅ | |

**의견: 새 라이브러리를 도입하지 마십시오.** 이 모듈 하나 때문에 Prisma·TanStack Query·Zod를 들이면 코드베이스가 두 갈래로 갈라지고, 이후 모든 작업이 "어느 쪽 패턴이냐"를 먼저 판단해야 합니다. 배송관리가 기존 패턴으로 잘 돌아가고 있으니 그대로 따르는 편이 낫습니다.

### 9.1 일정에 대한 단서

**총 9~12주** (Phase 1~4, 1인 개발 기준). v1의 7.5~8.5주보다 늘렸습니다.

비교 근거 — 배송관리 모듈은 테이블 2개(`shipments`, `shipment_log`) + 화면 3개 + 크론 1개 규모였고, 저장소·화면 코드가 약 1,650줄입니다. 임대차는 **테이블 6개 + 화면 8개 + 리포트 엔진**이라 최소 2배 규모입니다.

다만 이건 추정입니다. **Phase 1을 끝내고 나면 실제 속도가 나오므로, 그때 남은 일정을 다시 잡으십시오.**

## 10. 우선 확정이 필요한 사항

| # | 확인 사항 | 상태 | 영향 |
|---|---|---|---|
| 1 | 라스온 숍인숍(병원·카페 등)은 임대차인가, 수수료 매장인가? | ❓ **업무 확인 필요** | 매출연동형 임차료(`calc_type=매출연동`) 필요 여부 |

| 3 | 임차료 납부 주체가 본사 단일인가, 매장별 분산인가? | ❓ **업무 확인 필요** | 납부 기록 단위 |
| 4 | 회계기준: 일반기업회계기준 / K-IFRS 중 무엇인가? | ❓ **업무 확인 필요** | 4.6 리스회계 범위 |
| 5 | 회계부서가 지금 매달 만드는 엑셀 양식 실물 3~5종 | ❓ **업무 확인 필요** | R-03·Phase 4 설계 정확도 |
| 6 | 기존 매장 테이블에 소재지·면적 필드가 있는가? | ✅ **확인 완료** | 있음. 단 면적이 `TEXT`이고 생애주기가 달라 **계약 스냅샷으로 별도 저장**(4.3) |
| 7 | 권한 체크가 권한 코드 기반인가, 역할명 하드코딩인가? | ✅ **확인 완료** | 경로 정책표 + `roles TEXT[]`. **리팩터링 불필요**(7.1) |

> **#5(현행 엑셀 양식 실물)** 가 가장 중요합니다. Phase 1의 R-03을 그 양식에 맞춰 내야 회계부서가 바로 쓸 수 있습니다. 착수 전 수집을 권장합니다.

## 11. 리스크

| 리스크 | 대응 |
|---|---|
| 매장 급증으로 계약 등록 자체가 병목 | **Phase 1에 엑셀 일괄 업로드 포함** (검토가 아니라 필수 항목으로 승격) |
| 회계 보고서 요구가 계속 추가됨 | Phase 1에 실물 1종 → Phase 4에 엔진 일반화 (6.1) |
| 월별 스케줄 행 폭증 | 예정액을 저장하지 않고 계산 (4.5) |
| 기존 계약관리와 개념 혼동 | 메뉴·용어를 "임대차계약"으로 분리, 코드 네임스페이스 `lease/` 분리 |
| 임대료·보증금 정보 노출 | 기본 비공개 + fail-closed 정책표 (7.4) |
| 1인 개발 리소스 한계 | Phase별 독립 배포, Phase 4 이후는 요구 발생 시에만 진행 |
| 두 PC 개발 환경 | 착수 전 `git pull`, 완료 후 즉시 커밋·푸시. 배포는 git과 무관하게 동작하므로 **배포했다고 저장소에 반영되지 않음** |
